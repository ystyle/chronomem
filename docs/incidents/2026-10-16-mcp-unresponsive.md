## 是「卡死」还是「极慢」？——进程仍在干活，不是死锁

| 观察 | 结果 | 含义 |
|---|---|---|
| 最轻请求 `tools/list`，超时 120s | `http=000`，无响应 | MCP 路径确实不可用 |
| 同容器 `GET /` | 200，1.57s | 不是网络 / 容器整体问题 |
| CPU 累计（`utime+stime`）5 秒两次采样 | 994326 → 994427（**+101 jiffies ≈ 1 核**） | **进程在消耗 CPU，不是空转等待** |
| 11 个线程的状态 | **全部 `S`（sleeping）** | 无自旋、无典型死锁 |
| 内存 | 969 MB → 921 MB（缓慢下降） | GC 仍在回收 |

所以不是死锁，而是 **MCP 处理路径被拖到无法在合理时间内完成响应**：CPU 在烧、
线程在睡（等 I/O 或定时器），而请求始终不返回。

一个与现象吻合的解释（**待验证，非结论**）：JSON-RPC 处理是串行的，一旦某个请求
（或它触发的物化 / 总结任务）长时间占用处理链，后续请求就全部排队 —— 而 `/` 是独立的
HTTP 静态路径，因此不受影响。这与「健康检查探 `/` 所以误报 healthy」是同一个原因。

## 3. 机制：内存压力如何让 `/mcp` 无响应，而 `/` 正常

架构已核实（`mcp-cj` 的 `StreamableHttpServer_2025_11_25`）：

- HTTP 请求线程只做**入队 + 有界等待**（`awaitResponse`，默认 5 分钟超时）；
- 真正的处理在**单个消费线程**上串行（`receive()` 一次取一条 → jsonrpc `receiveLoop` 严格串行）；
- 所以**任一请求变慢，后续 `/mcp` 请求就全部排队** —— 原文这一推断正确；
- `GET /` 是独立的静态路径（`compose.setFallback(uiApp.router())`），不经过该队列，
  故始终 200 —— **这也正是健康检查（探 `/`）误报 healthy 的原因**，原文这点也正确。

**修正后的根因表述**：不是「物化卡住导致排队」，而是**堆接近满值 → GC 频繁但回收不动 →
分配/处理被大幅拖慢 → 串行处理链上的请求排队超出客户端超时**。
物化只是恰好每 60 s 跑一次、在日志里留下高频痕迹，不是阻塞者。

排除项（复核确认，与原文一致）：**fd 10 个、线程 11 个**，无连接/线程泄漏。
