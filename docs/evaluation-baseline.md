# 忆时塔（Chronomem）运行数据评估：现在能不能写实证论文

> **日期**：2026-10-14
> **结论先行**：**不能**。当前数据足以支撑「系统正确性与运行成本」类结论，但**不足以支撑实证论文**——缺的是对照实验，不是数据量。
> **本文目的**：把三次实测（09-29 体检 / 10-10 首查 / 10-14 复测）合并为同一份基线，并明确「已有什么、缺什么」。

## 1. 三次实测的关系

| 日期 | 类型 | 发现 |
|---|---|---|
| **09-29 11:50** | 全量窗口一致性体检 | **找出 2 类静默正确性缺陷**（8 处不一致） |
| **09-29 12:10** | 修复 | 修 + 部署 + 87 窗口复验全绿 |
| **10-10 11:39** | 只读回溯核查 | 四条回溯路径实测 + 修复后回归确认 |
| **10-14 02:15** | 复测（本文） | 三个数据源合并 + 修复仍生效 |

**为什么这件事影响论文**：09-29 体检的原话是——

> 「若要从 position 升级为实证论文，须先修上述 ①②，否则**『精确回想 = 无损导航』这一核心主张会被自身数据证伪**。」

即：论文的核心卖点（exact recall 无损、零 LLM 的精确导航）如果自身实现有丢条目/串窗口的问题，实证数据一测就自相矛盾。

## 2. 09-29 体检发现了什么（历史缺陷）

| 缺陷 | 具体表现 | 根因 |
|---|---|---|
| **① 桶陈旧丢条目** | `dsh/activity` 09-12 窗口**实际 48 条，桶只有 28 条**——`exact` 下钻永久看不到那 20 条 | `materializeMissingClosed` 以「桶是否存在」为补齐判据；服务中断后桶停在中断前点数，之后新增条目永不进桶 |
| **② 空窗口串数据** | 查无记录时段（09-17~09-20、09-25）**返回上一个有记录时段的数据**。实测 09-25 `query=0` 条，`exact` 却返回 09-24 的 6 条（字节完全相同） | `bucketAt` 在目标窗口无桶时**回退到最近的更早桶**，`recall exact` 直接沿用且无提示 |

**核对范围 8 个窗口不一致**（7 个串数据 + 1 个丢 20 条）。

**修复**（同日 12:10 上线）：
- 幂等判据从「桶是否存在」改为**内容指纹**（点数未变仍不重写，保持幂等）
- `bucketAt` 增加 `allowFallback`（**默认 false = 严格**）；`exact` 分支区分「无记录」与「有记录但未物化」

**修复后验收**：09-12 桶由 28 重算为 48；**09-01~09-29 × 3 类型共 87 窗口一致**（修复前 8 处不一致）。

## 3. 10-14 复测（本文实测）

### 3.1 语料规模（三个数据源）

| 类型 | 条目 | day 桶 | week 桶 | 备注 |
|---|---|---|---|---|
| `worklog` | **463** | 37 | 8 | 人工写（项目任务账） |
| `dsh/activity` | **1112** | 27 | 5 | **全自动**（dsh 宿主插件写入） |
| `dsh/lesson` | **58** | — | — | 手动写，不自动总结 |

**增长趋势**（对照 10-10 首查）：

```
worklog      431 → 463   (+32)
dsh/activity 949 → 1112  (+163)
day 桶        33 →  37
```

即：**连续运行约 2 个月**（2026-08-29 起），语料已稳过千级，且仍在自然增长。

### 3.2 三口径一致性（沿用 09-29 的方法）

方法：**物化桶计数（`mem/buckets`）vs 直接查询计数（`mem/query`）vs exact 下钻（`mem/recall mode=exact`）三者应相等**。

单口径自检**无法**暴露「桶陈旧」与「串窗口」这两类静默缺陷——只有交叉比对能。

**复测结果**：

| 检查 | 结果 |
|---|---|
| `dsh/activity` **09-12 CST**（曾 28 vs 48） | 桶 **48** / exact **48** ✅ **一致** |
| `worklog` **09-17**（曾串数据） | exact 返回「该时间窗无记录」✅ **不再串窗** |
| week 桶覆盖子桶数 vs 实际 day 桶分布 | 对得上（08-31 周 = 7 个日桶、09-14 周 = 3 个…）✅ **链未断裂** |

**结论：09-29 的修复在近 2 周后仍生效**，核心主张「精确回想 = 无损导航」在自证口径上成立。

## 4. 能写什么、不能写什么

### ✅ 现在就能支撑的结论

- **系统正确性**：三口径一致、87 窗口复验、修复前后对照（8 → 0 处不一致）
- **运行成本**：压缩比、切块行为、延迟、内存
- **语料真实性**：连续近 2 个月、1500+ 条真实记录、自动采集
- **工程决策**：模型选型 A/B、参数标定（这些是"怎么做"，不是"比别人好"）

### ❌ 实证论文必需但**缺失**的

| 缺什么 | 为什么必需 |
|---|---|
| **对照实验** | 全是"自证运行正常"，**没有** Chronomem vs flat memory vs one-shot compaction 的准确率/token 曲线。没有对照，"分层记忆更好"无从谈起 |
| **语义漂移量化** | 递归压缩是论文核心主张之一，但**从未测过**每层衰减。压缩比 5.1x 只证明"压了多少"，不证明"压得对不对" |
| **调度策略实测** | settle/backoff/上限等 5 道护栏是设计亮点，但没有"不同参数下的 token 消耗"数据 |
| **任务级准确率** | 没有 QA 题集、没有 ground truth、没有人评 |

**一句话**：现有数据是**「系统跑得对不对」**，实证论文要的是**「比替代方案好不好」**。前者是后者的前提，但不能替代。

## 5. 建议路径

1. **position 论文（已投 AiraXiv v2，6.6/10）保持 position 定位**——不要在它里面硬塞实证。它的 §6 已写明「实证留后续论文」。
2. **若要做实证论文**，最小可行实验（评审给的最低门槛）：
   - N=3 agents × 7 模拟天
   - 三组对照：Chronomem 默认 / flat recency / one-shot compaction
   - 指标：50 题 QA 准确率 + 服务端 token + 存储增长
   - 评审原话：「**still better than none**」
3. **先固化本文这份基线**（一致性方法 + 语料统计），它是实证论文的**前提证据**：证明"测量工具本身可信"。

## 6. 复现方法

```bash
# 三口径交叉验证（只读，零 LLM）
mem/buckets  { type: "<type>", granularity: "day" }         # 桶计数
mem/query    { type: "<type>", from: <start>, to: <end> }   # 直接计数
mem/recall   { type: "<type>", granularity: "day", mode: "exact",
               windowStartMs: <start> }                      # 下钻计数
# 三者应相等；空窗口应返回「该时间窗无记录」而非上一窗口数据
```
